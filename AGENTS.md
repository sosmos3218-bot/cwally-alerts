## On-time external trigger

GitHub schedule events arrive hours late. On-time runs come from an external cron calling `workflow_dispatch` for the morning / afternoon / flow / 0090b0 / k203780 (19:00) slots; see `docs/ontime-dispatch.md`. `scripts/slot_guard.py` + `state/slots/<slot>.json` let each slot run once per KST day, so a late GitHub cron or a duplicate dispatch skips. Keep the GitHub crons as the fallback.
One-shots are on time the same way: the external cron dispatches `job=oneshot` at each `oneshot_kst` time, and `scripts/oneshot_pick.py` runs every one-shot whose time is within the last 60 minutes and not yet recorded in `state/slots/oneshot.json` (key `<name>@<YYYY-MM-DD HH:MM>`). A late GitHub one-shot cron checks that file and skips an occurrence that already ran. An occurrence is recorded *before* its script runs, so a failed script is not re-sent by the fallback; it raises the ops notice instead, and a manual retry is a dispatch of that alert's job id (if listed) or a `force` run of its script. One-shot times at 09:00 / 15:20 for alerts already in that slot bundle are left to the slot. KRX holidays live in `scripts/kr_calendar.py` (update every December).

## One-off briefs (outbox)

Approved in chat 2026-10-23 20:08 KST. Scheduled assistants deliver ad-hoc written summaries (for example an earnings recap) through this repo, never by posting to ntfy directly.

- File: `outbox/<YYYYMMDD>-<slug>.json`, UTF-8 JSON object:
  `{"topic": "cwally-port" | "cwally-ops", "title": "[BRIEF] ...", "body": "text (markdown ok)", "priority": 1-5, "tags": ["memo"]}`.
  `topic` and `title` are required; `body` defaults to `""`, `priority` to 3, `tags` to `["memo"]`. Any other topic is rejected (notice to `cwally-ops`). Unknown keys are ignored.
- Title must start with a prefix: `[BRIEF]` for general briefs, or a topic-specific one such as `[EARN]` for earnings recaps. A title without a leading `[...]` gets `[BRIEF] ` prepended. Briefs are free text and do not need the six-item body order; `ntfy_util.publish()` still appends the end line.
- Korean text rule: never use the middle dot (`·`) or the em-dash (`—`) in title or body. The sender does not rewrite text; it only logs a warning.
- Send: commit the file to `main`, then run `gh workflow run port-alerts.yml -R sosmos3218-bot/cwally-alerts --ref main -f job=brief -f oneoff_mode=auto`. Any other `oneoff_mode` (default `dry`) runs the selftest and prints what would be sent (no ntfy, no state).
- `scripts/brief_monitor.py` sends every outbox file not yet in `state/brief.json` (key = filename + sha256 of the file bytes), so re-dispatching does not resend; editing a file's content makes it a new brief. A body over `message_max_bytes` (3900 bytes, under ntfy's 4096-byte limit) is split into numbered parts, title suffix ` (1/n)`, never truncated. A failed send raises a `cwally-ops` notice and the next `job=brief` run resumes from the failed part.
- It runs only on `workflow_dispatch` with `job=brief`, never on scheduled slots. Archive and state commit are the normal `Archive ntfy` / `Persist state` steps. Do not add outbox files for testing; use `python scripts/brief_monitor.py selftest` or a dry dispatch.

## ntfy copy style

Write every alert so a tired reader knows what to do in 5 seconds. Korean, short sentences, no unexplained jargon.

Required body order:
1. 이게 뭐 알림
2. 지금 결과/상태
3. 지금 할 일
4. 나중에
5. 익절/줄일 때
6. 하지 말 것
7. 꼬지는 때 (자동: `ntfy_util`이 `ends_kst`/`ends_note`로 맨 끝에 붙임. 본문에 직접 쓰지 않는다)

Title format: `[NAME] 한 줄 행동`
Example: `[HCE] 아직 결과 없음 | 추가매수 보류`

Template: `configs/alert_copy.json`. Helper: `scripts/ntfy_util.py`.
## Workflow file edit rules

- Never rewrite a whole `.github/workflows/*.yml` file. Change only the lines you need (minimal diff), starting from the current main content.
- Never commit placeholder text such as "truncated for brevity" or "rest unchanged". `.github/workflows/workflow-lint.yml` fails on it, on a missing `jobs:`/`on:`, on a >20% line-count drop (override only with `[allow-shrink]` in the commit message), and on actionlint syntax errors.
- Exception (approved in chat 2026-10-13): `workflow-lint.yml` is allowed as an extra workflow file. It runs on push/PR only, has no schedule, and is read-only. This does not allow any other new workflow file.
- Before committing a workflow edit, fetch the current file, apply the edit, and check that the line count did not shrink unexpectedly. After committing, confirm the push-triggered run is not a Failure.
- If a workflow file is found broken, restore it from the last good commit first, then re-apply the intended change as a minimal diff.
- Shared workflow files (approved in chat 2026-10-16): immediately before editing any `.github/workflows/*.yml`, fetch the current main version again; never edit from an older copy. Right after pushing, check the push-triggered `workflow-lint` run; if it fails, restore the file from the last good commit first, then re-apply the change as a minimal diff.

### Re-prevention checklist (added 2026-10-19 after truncated port-alerts.yml incident)
- Before any edit to `.github/workflows/*.yml`: `gh api .../contents/<file>` (or get_file_contents) to fetch the exact current main blob, never work from a local/cached/truncated copy.
- Apply only the minimal line additions or changes. After edit, run `wc -l` and compare to the previous version; a drop >5% on a large file requires explicit confirmation.
- Forbidden strings that workflow-lint will reject: `truncated for brevity`, `rest of the file`, `rest unchanged`, `full content from /tmp`, `PLACEHOLDER`, `TODO: restore`.
- After push, immediately check the workflow-lint run conclusion. If failure, restore from the last successful commit SHA before any further edits.
- When adding oneshot crons, copy the exact existing pattern (comment + 3 cron lines + elif extension) from a similar alert; do not regenerate the whole file.
- `port-alerts.yml` full-overwrite ban (approved in chat 2026-10-19 after 5 placeholder overwrites): never send the whole `port-alerts.yml` through the GitHub connector (`create_or_update_file`, `push_files`) or any tool that takes the full file body. Edit it only with `git clone` + a line-level edit + `git push`, and the commit diff must touch only the lines you add or change. If you cannot do that, stop and ask the user instead of pushing. Never push text such as "FULL_CONTENT_FROM_", "FROM_LOCAL_FILE", or "partial restore placeholder".
